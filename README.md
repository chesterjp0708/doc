二段階で開発します。
まず、関数や単一ファイルを変換できる独立ツール cpp2py-core を実装し、実際のC++コードで精度を検証します。
次に、cpp2py-core を利用して、モジュール単位の分析・変換・テストを行う移行システムを構築します。元のC++にテストがない場合は、実行結果を記録してPython版と比較します。
AIは分析・変換・テスト生成を支援しますが、ビルド、差分比較、承認は自動ツールと担当者が行います。
最終的な方針は、小さなコード変換から始め、実績を確認しながらモジュール移行へ拡張することです。


# C++ → Python 移行ツール計画

## 1. 基本方針

本プロジェクトは、次の二つに分けて実装する。

1. **`cpp2py-core`**
   - C++ の関数、コード断片、単一ファイルを Python に変換する。
   - 単独で利用できる製品として最初に完成させる。
   - 後続のモジュール移行でも同じ変換エンジンを利用する。

2. **`cpp2py-migrate`**
   - 既存 C++ プロジェクトの業務モジュール単位で分析・変換・検証する。
   - 他チームの内部実装を読む必要はなく、公開インターフェースだけを参照する。

正式な移行単位はモジュールだが、関数やファイルだけを変換したい場合は `cpp2py-core` を直接使える。

---

## 2. 最初に `cpp2py-core` を実装する

モジュール分析やレビュー画面より先に、`cpp2py-core` を独立してリリースする。

利用例：

```powershell
cpp2py convert function replace_all.cpp

cpp2py convert file OrderCalculator.cpp `
  --header OrderCalculator.h `
  --compile-db build/compile_commands.json
```

### 変換モード

- **Raw mode**：ビルド情報がないコード断片向け。未解決の型や依存関係を明示する。
- **Semantic mode**：clang と `compile_commands.json` を使用し、実際の型、オーバーロード、マクロ情報を取得する。

### 内部処理

```text
C++ source
  → clang semantic extraction
  → Source IR
  → mapping rules + Conversion Agent
  → Python checks
  → Python code + report
```

AI は意味変換を担当し、AST 解析、ビルド、構文確認、テスト実行は通常のプログラムで行う。

### 初期リリースの完了条件

- 関数、断片、ファイルを単独で変換できる。
- Raw/Semantic mode を区別できる。
- 未対応処理を黙って削除しない。
- 出力した Python が parse/import できる。
- ユーザー提供テストを実行できる。
- CLI と SDK が同じ変換エンジンを使う。
- 実際の C++ コードで評価済みである。

この条件を満たす前に、大規模なマルチ Agent 機能を追加しない。

---

## 3. 共通移行ルール

各担当者は自分のモジュールだけを移行するが、次の設定は全員で共有する。

```text
migration-spec/
├── target-profile.yaml
├── exception-mapping.yaml
├── transaction-policy.yaml
├── shared-models/
├── contracts/
└── decisions/
```

共通化する内容：

- Python/Web フレームワーク。
- DB アクセス方式とトランザクション方針。
- 共通モデルと例外。
- モジュール間インターフェース。
- 日時、金額、null、認証などの規則。

C++ のクラス階層、ポインタ、スレッド構造をそのままコピーする必要はない。維持すべきなのは公開 API、データの意味、DB 制約、エラー、権限、原子性などの観測可能な仕様である。

---

## 4. モジュール移行

入力：

```text
module source/header
+ build target
+ public interfaces
+ external contracts
+ migration-spec
```

処理：

```text
モジュール分析
→ 契約と依存関係の確認
→ 必要に応じて C++ の動作を観測
→ Python 移行設計
→ cpp2py-core で変換
→ C++/Python 差分テスト
→ 高リスク差分を人が確認
→ モジュール移行パッケージを出力
```

出力には Python コードだけでなく、テスト、契約、未確認項目、変換根拠も含める。

---

## 5. AI Agent

Agent は必要な推論処理だけに使う。

### Module Analysis Agent

- モジュール入口、公開機能、外部依存を整理する。
- 状態、エラー、副作用、トランザクション候補を抽出する。
- 各結論にソース位置や実行結果を付ける。
- 不明な内容を事実として扱わない。

### Behavior & Test Agent

- 分析結果を実行可能な確認項目に変換する。
- C++ Test Harness、境界値、異常、並行実行テストを作成する。
- 実行結果を少数の行動ルールにまとめる。

### Migration Planning Agent

- 共通ルールに従って Python モジュール構造を設計する。
- Router、Schema、Service、Repository の配置を決める。
- 自動変換、再設計、人の確認が必要な部分を分ける。

### Module Conversion Agent

- `cpp2py-core` を利用してコードを変換する。
- モジュール全体で必要なリファクタリングを行う。
- 元コード、契約、Python 実装の対応関係を保存する。

### Failure Analysis Agent

- ビルドやテスト失敗の原因を分類する。
- 実装、テスト、共通ルール、環境、元 C++ の問題を区別する。
- 最小修正案を作るが、自分で結果を承認しない。

オーケストレーション、ビルド、差分比較、バージョン管理は AI Agent ではなく通常のプログラムで行う。

---

## 6. C++ にテストがない場合

Test Harness を生成し、原 C++ モジュールを実行して次を記録する。

- 戻り値と例外。
- DB の変更。
- ファイル変更。
- 外部サービス呼び出し。
- 重要な副作用。

最初から AI の予想値を assertion にしない。

```text
AI が仮説を出す
→ Harness で C++ を観測する
→ 実際の結果を記録する
→ 高リスク・矛盾だけ人が確認する
→ Characterization Test として固定する
→ 同じ入力で Python と比較する
```

元 C++ と一致しても、元の仕様自体が正しいとは限らない。バグと思われる動作は「維持」「Python で修正」「未確定」に分類する。

---

## 7. 人の確認と修正

人は個々の大量テストを確認せず、AI がまとめた行動ルールと差分だけを確認する。

必須確認項目：

- ドキュメントと実行結果の矛盾。
- 金額、在庫、認証、トランザクション。
- データ損失の可能性。
- C++ と Python で一致しない動作。
- 元 C++ のバグの可能性。
- 意図的に仕様を変更する場合。

修正時は必ず最小再現テストを追加する。プロンプトだけを変更して同じ処理を再実行する方法は採用しない。

共通モデルや契約はバージョン管理し、変更の影響を受けるモジュールを `needs_revalidation` に戻す。

---

## 8. 実装順序

1. **`cpp2py-core`**
   - CLI/SDK、clang IR、変換 Agent、静的確認、レポート。
2. **モジュール分析と共通仕様**
   - module manifest、契約、証拠、バージョン管理。
3. **テストがないモジュールの観測**
   - Harness、C++ runner、行動ルール、Characterization Test。
4. **モジュール変換と差分検証**
   - Python モジュール生成、差分テスト、障害分析。
5. **複数担当者によるレビュー**
   - 契約の相互確認、変更影響、回帰テスト管理。

最初の MVP は一つの技術経路に限定する。例：

```text
CMake + Drogon + PostgreSQL
→ FastAPI + Pydantic + SQLAlchemy Async + pytest
```

他のフレームワーク対応は、最初の経路を実プロジェクトで検証した後に追加する。

---

## 9. 最終的な判断基準

`cpp2py-core` は、単独ツールとして実用可能であることを先に確認する。

モジュール移行は次を満たす必要がある。

- 分析結果に根拠がある。
- 公開契約と外部依存が明確である。
- C++ の実動作を観測できている。
- Python モジュールが起動できる。
- 確認済みシナリオで差分テストに合格する。
- 未確認の高リスク項目が明示される。
- 人の修正が回帰テストとして残る。

この順序により、小規模なコード変換を早期に利用しながら、後からモジュール単位の信頼性とチーム運用を追加できる。
