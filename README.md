既存のWord設計書と現行ソースコードを調査し、既存設計書と同じ構成の「現行実装に基づく設計書」と、「既存設計書・現行実装の対照資料」をMarkdown形式で作成してください。

■ 入力

・既存のWord設計書：［ファイルまたはフォルダーを指定］
・現行ソースコード：［ソースのルートフォルダーを指定］
・対象機能：［対象機能を指定］
・出力先：［出力フォルダーを指定］

■ 基本方針

既存設計書は、章立て、項目構成、記述粒度、用語、表や図の形式を引き継ぐための基準とします。
現行ソースコードは、実装されている処理内容を確認するための基準とします。

既存設計書の記述を、そのまま現行実装の事実として採用しないでください。
また、設計と実装に差異があっても、実装が正しい、または設計書が誤っているとは断定しないでください。

■ 作業手順

1. 既存Word設計書を読む

本文だけでなく、表、図、注記、脚注を確認し、以下を把握してください。

・章と節の順序、番号、見出し
・各項目の目的と記述粒度
・表の列構成と項目の並び
・業務フロー図の表現方法
・業務用語、状態名、入出力の名称

画像として埋め込まれた図も確認してください。
読み取れない箇所は明示し、内容を推測で補完しないでください。

2. 現行ソースコードを調査する

設計書の各項目に対応する実装を特定し、必要な呼び出し先、共通処理、設定、データ操作まで追跡してください。

確認対象：
・開始条件と入力
・処理対象の決定方法
・処理順序と分岐条件
・業務ルールと計算内容
・出力と成果物
・状態の更新
・異常、停止、終了時の動作
・外部機能との連携

現行の実行経路と、コメントアウトされた旧処理を区別してください。
コメントや関数名だけで処理内容を断定せず、実装内容を確認してください。

3. 既存設計書と実装を対応付ける

設計書の各項目について、対応する実装と確認結果を整理してください。
設計書にない実装と、実装を確認できない設計項目も記録してください。

対象範囲の調査だけでは判断できない場合は、「未確認」としてください。
実装が見つからないことだけを理由に、「未実装」と断定しないでください。

■ 成果物1：現行実装に基づく設計書

ファイル名：
［対象機能名］_現行実装設計書.md

既存Word設計書の章立て、見出し、項目順、表の列構成、記述粒度を可能な限り維持し、内容を現行実装に基づいて記述してください。

「同じ形式」とは、文書の論理構成と表現形式の継承を意味します。
Word固有の改ページ、フォント、余白など、Markdownで再現できない外観の完全一致は求めません。

記述条件：
・既存設計書と対応を追えるよう、章・節番号を維持する。
・独自の要約構成に置き換えない。
・表は原則として元の列構成を維持する。
・処理フロー図は、元の図の目的と粒度を維持し、Mermaidで表現する。
・既存設計書が業務レベルの説明であれば、コードの内容を業務用語に置き換えて記述する。
・本文や図に、説明上不要なコード、関数名、変数名、SQL、戻り値を追加しない。
・既存設計書に技術仕様欄がある場合は、その欄の目的に必要な技術情報を記載する。
・コードから確認できない業務目的、運用手順、担当者、性能値は創作しない。
・既存資料だけを根拠として残す情報は、「既存設計書記載・実装未確認」と明示する。
・対応する実装を確認できない項目も削除せず、その確認状況を記載する。
・実装にのみ存在する内容は、関連する既存項目へ記載する。
  適切な項目がない場合に限り、末尾に補足節を追加する。

この設計書は、現行実装の内容を独立して読める文書にしてください。
旧設計との詳細な比較、修正履歴、調査の経緯は成果物2に記載してください。

■ 成果物2：既存設計書・現行実装の対照資料

ファイル名：
［対象機能名］_設計実装対照.md

以下を記載してください。

1. 比較対象と調査範囲
   既存設計書の名称・版、ソースの対象範囲、確認できる場合はコミット識別子を記録する。

2. 比較結果の概要
   一致している範囲、主な差異、業務上の影響、未確認事項を簡潔に整理する。

3. 項目別対照表
   次の列を使用する。

   ・対照番号
   ・既存設計書の章・節・項目
   ・既存設計書の記載内容
   ・現行実装で確認した内容
   ・判定
   ・差異と業務上の影響
   ・実装根拠
   ・現行実装設計書の対応箇所
   ・追加確認事項

判定は以下を区別してください。
・一致
・差異あり
・設計書に記載なし
・対応実装を確認できず
・調査範囲外

差異のある項目だけでなく、一致した項目も対応付けてください。
表の各行は、確認・判断できる単位に分けてください。

実装根拠には、ソースファイルのパス、関数名、該当行など、再確認できる位置情報を記載してください。ソースコードの長文転載は避けてください。

業務上の影響を断定できない場合は、「影響未確認」と記載してください。
変更理由や変更時期は、履歴などの根拠がない限り推測しないでください。

4. 追加確認事項
   確認すべき内容、必要な資料、確認できないことによる判断上の制約を整理する。

5. 形式上の差異
   WordからMarkdownへの変換で再現できなかった表現と、採用した代替表現を記録する。

■ 最終確認

提出前に以下を確認してください。

・既存設計書の全項目に、記載先または未確認の説明があること
・現行実装設計書と対照資料の記述が矛盾しないこと
・処理順序、分岐条件、終了条件が実装根拠と一致すること
・正常完了、異常終了、未実施、停止を混同していないこと
・旧処理や推測を、現行実装の確定事項として扱っていないこと
・図、表、本文の内容が一致すること
・過去の修正指示、重複説明、旧結論などの編集上の残骸がないこと

入力資料が不足している場合も、確認可能な範囲の作業を進め、不足内容と影響を明示してください。

原本のWord設計書とソースコードは変更しないでください。
成果物はすべて日本語で作成してください。
完了時に、2つの成果物へのリンク、主要な差異、残る未確認事項を簡潔に提示してください。

AIは、プロジェクト全体を自由に変換する目的では使用しません。通常の変換ルールでは対応できない一部の関数を補助するために利用します。
AIが生成したコードは、そのまま採用しません。
安全性の確認と、元のC++との実行結果の比較を行い、検証を通過した場合のみ候補として採用します。
現在は会社のAIアカウントがまだ発行されていないため、主に全体の処理手順と管理方法を確認した段階です。
